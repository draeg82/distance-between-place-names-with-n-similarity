# One generated place database replaces choosing between dumps

The three committed dumps are nested by GeoNames id: every id in `cities5000.txt` is also in
`cities1000.txt`, and every id in `cities15000.txt` is in both. So "which dataset should this
search use?" is a choice between three copies of overlapping places, and a search over
`cities1000.txt` silently re-reads places it has already seen. The tool instead generates one
SQLite table of places, deduplicated by GeoNames id, from all three dumps: 230,160 input rows
become 146,782 places.

Each place is recorded by the **smallest population threshold whose dump contained it**, in a
`source_threshold` column, so a place can still be traced to the most inclusive dump that
listed it. Because the dumps are nested by id but not by population, that field says which
dumps were available to an import rather than which ones exist: importing only
`cities5000.txt` and `cities15000.txt` records every place at 5000.

The database is a build artefact. It is generated by `distnsimilarity-import` into
`places.sqlite3` beside the dumps, is git-ignored, and is never committed: it is 17 MB of
derived data, rebuilt from the 41 MB of dumps it comes from in about a second.

## Consequences

A fresh clone can run a terminal search over the dumps, but the database is empty until
something has been imported. `connect()` creates an empty schema rather than failing, and a
search over an empty table raises
`DatabaseNotImportedError` naming the command that fixes it - an un-imported database is a
state the tool expects, not a corrupt file.

Re-importing is safe: the insert is `INSERT OR IGNORE` keyed on GeoNames id, so a second
import adds nothing and changes nothing. That also means a place keeps the values of the dump
that first recorded it; the copies of the same id in the other dumps are ignored rather than
merged. The dumps agree on the fields this tool reads, so nothing is lost today, and a future
disagreement would be an import-time decision rather than a silent merge.

A schema version in `PRAGMA user_version` refuses a database from a newer version instead of
misreading it. Rebuilding is `--recreate`.

The database is read-mostly, so it is opened in WAL mode: the search API can read while a
scan is running. Writing while reading is the import's job, and one import at a time is a
restriction the API has to respect when it grows a reload endpoint.

Candidate generation moved onto the database - name-length groups and a population floor are
SQL lookups now - so it is part of the seam, not an adapter: it decides what gets compared,
which is a rule. Matching and distance stay in `distnsimilarity.core`, and both candidate
paths hand their pairs to the same inner loop.
